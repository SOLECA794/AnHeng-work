# 规格库（SDD 治理范式）

本目录是项目的**规格库**，采用 **SDD（Spec-Driven Development，规格驱动开发）** 治理范式：一切开发、测试与验收以规格为源头，规格 → 实现 → 测试 → 验收 全程可追溯。

## 为什么用 SDD

本项目是"先定规格、后交开发"的工程模式（赛题明确要求交付架构、工具清单、源码、部署说明与测试报告）。SDD 保证：

1. **需求有据**：每个功能都能在需求规格（SRS）中找到条目；
2. **设计可循**：每个需求都有对应设计规格（SDD）支撑；
3. **测试可依**：测试用例与需求条目、设计实现一一对应；
4. **验收可查**：验收标准直接对齐赛题评价指标。

## 规格分层与编号

| 层级 | 目录 | 编号前缀 | 内容 |
| --- | --- | --- | --- |
| 需求规格 | `01-需求规格/` | SRS | 项目概述、需求基线、功能规格说明书 |
| 设计规格 | `02-设计规格/` | SDD | 系统架构、数据模型、接口规格 |
| 测试规格 | `03-测试规格/` | TEST | 测试计划、用例设计、测试集说明 |

编号规则：`<前缀>-<序号>-<名称>.md`，如 `SRS-01-项目概述与需求基线.md`。

## 规格状态机

```
草案(Draft) → 评审(Review) → 基线(Baseline) → 变更(Change) → 新基线
```

- 规格进入**基线**状态后，开发、测试方可引用，不得直接修改；
- 变更必须走变更记录：在规格文件末尾的「变更记录」表登记（版本、日期、变更人、变更内容、影响范围）；
- 规格与实现不一致时，先改规格（评审）再改实现，禁止"先改代码后补文档"。

## 追溯关系

| 方向 | 关系 |
| --- | --- |
| 需求 → 设计 | SRS 功能条目（F 编号）在 SDD 中有对应设计小节 |
| 设计 → 实现 | SDD 模块在 `src/` 中有对应目录/模块 |
| 需求 → 测试 | TEST 用例引用 SRS 功能条目编号 |
| 评价指标 → 验收 | `docs/02-质量与验收/01-验收标准-对齐赛题评价指标.md` 逐项映射 |
