实现 `AlertService`、SQLAlchemy 仓储和 SDD-03 三个管理接口的路由工厂。默认 HIGH 阈值，篡改/敏感信息另行触发，INFO 和误报不告警；规则从 `src/config/alert-policy.json` 加载，支持禁用、阈值与类型配置及策略 SHA256。站内通知即已持久化的告警收件箱，没有外发邮件或群消息。

## 2. 如何去重与复现

以 `(scope_id, dedup_key)` 区分风险，跨轮次、跨 Finding ID 仍使用同一周期。重复任务最多生成一次；将告警已读、处理或关闭都不会清除去重状态。

例如风险 #101 首次出现产生告警；下次任务发现相同身份只记录重复。之后 T25 将 Finding 持久化为 FIXED，并调用本服务记录修复边界；再出现 last_seen 晚于修复时间的新检测，才产生第二个周期的告警。旧任务或同秒的观测保守按过期处理，不会回退水位或重开周期。服务不会自行把风险标记为修复。

周期状态保存在同身份最早 Finding 的 `raw_data.alerting`：version、phase、cycle、watermark、alert_id。对已存在但缺少周期状态的告警，包含已关闭告警，先引导历史去重，不重发。损坏状态、告警指针错配或同 key 不同类型明确失败，不静默重建。

PostgreSQL 仓储先锁资产再锁风险，防止跨进程重复处理；同资产串行，吞吐需在生产联调时评估。SQLite 使用 BEGIN IMMEDIATE，实现测试中的独立连接竞争。告警、周期状态及成功操作审计同事务，审计失败全部回滚；周期元数据写入保留 Finding.updated_at，不伪造新的修复时间。

## 3. 调用与管理

```python
from src.repositories.alerts import SqlAlchemyAlertRepository
from src.services.alerts import AlertService, load_alert_policy
from src.api.alerts import create_alert_router

service = AlertService(SqlAlchemyAlertRepository(session_factory), load_alert_policy())
# principal 由真实鉴权取得，包含用户、角色和显式资产授权。
# 在检测或修复状态已经落库后调用：
receipt = service.process(finding_id, principal)
router = create_alert_router(service, principal_dependency=authenticated_principal)
# 由宿主在真实鉴权接通后显式挂载 router；本次不改默认应用。
```

| 路径 | 行为与权限 |
| --- | --- |
| GET /api/alerts?page=1&pageSize=20 | SEC_OPS/RULE_ADMIN；status/severity/scopeId 可筛选，限制显式授权且启用的资产 |
| POST /api/alerts/{id}/read | 三种已定义角色均可，仍须资产授权；全局已读标记幂等 |
| PATCH /api/alerts/{id}/status | SEC_OPS；请求 `{"status":"HANDLED"}` 或 `{"status":"CLOSED"}`，关闭后不能重开 |

没有注入可信身份时接口默认拒绝，伪造 X-Role/Authorization 头不能赋权。生成是内部服务方法，没有公开生成接口。process 结果包括 outcome、findingId、scopeId、cycle、alertId，仅首次生成返回 notification=IN_APP。

## 5. 集成边界

- 周期锚的身份、历史记录与 `raw_data.alerting` 必须保留，检测持久化更新不能用新 raw_data 覆盖它。正式装配须在相同资产锁约定下保留元数据，且检测、修复事件都要传递给本服务。
- 没有执行生产迁移或修改表结构；本次仅在隔离 SQLite 中验证事务和接口，PostgreSQL 行锁、实际鉴权、前端页面及在线巡检接入待联调。
- 本次交付站内收件箱。邮件是可选扩展，尚未配置外部发送渠道，不宣称邮件送达。
- 既有 read_status 是全局标志，并非每个用户独立已读；单用户收件与邮件重试需额外规格和实现。
