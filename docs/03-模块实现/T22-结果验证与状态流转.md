## 1. 今天处理的问题

检测命中先形成 `OPEN` 风险，但命中并不自动等于已确认风险。T22 提供人工确认与原始证据规则复核，让授权运维人员明确区分 `CONFIRMED` 与 `FALSE_POSITIVE`，并留下可查询的操作者、时间与原因。

本次实现只允许 `OPEN → CONFIRMED`、`OPEN → FALSE_POSITIVE`。对已经完成验证的记录，重复提交或改成另一结果都按状态冲突处理。修复后的新页面无命中属于 T25 复测，不回写成“原始风险误报”；严重级别调整属于下一项 T23。

本次已完成验证服务、SQLAlchemy 仓储、可注入认证依赖的 API 路由工厂、单元与 SQL/API 集成测试、离线验收脚本，以及 SDD-06 实现契约。实现复用主分支既有 Finding、AgentLog 模型，不依赖尚未合入的 T20 PR #1 或 T21 PR #2，也不修改生产数据库模式。服务、仓储和路由工厂已验收；T09 认证接入及生产挂载仍需集成。

## 2. 人工确认怎么操作

服务入口为：

```python
VerificationService.verify(
    finding_id, status, reason_code, principal,
    *, note=None, observed_at=None, expected_status="OPEN",
)
```

HTTP 写接口沿用基线：`PATCH /api/findings/{id}/status`，例如确认风险：

```json
{
  "status": "CONFIRMED",
  "reasonCode": "EVIDENCE_REVIEWED",
  "expectedStatus": "OPEN"
}
```

可省略 `expectedStatus`，但不能把它改成其他状态来绕过 OPEN 前置条件。标记误报时，原因必须是 `EXPECTED_PUBLIC_CONTENT`、`RULE_FALSE_MATCH` 或 `AUTHORIZED_CHANGE`。服务提供固定中文原因标签，便于查询和解释。

可选 `note` 最多 1000 字符，仅计算 SHA-256 摘要，不保存或回显说明原文。来源证据、网页内容及备注中的敏感信息不进入审计摘要或错误响应。服务端处理时间按上海时间精确到秒。

## 3. 谁能操作

调用方从 T09 的可信身份信息构造有效 `Principal`，明确用户 ID、角色与授权资产集合。服务逐项检查身份、角色、Finding 及资产范围。

| 操作 | 角色 |
| --- | --- |
| 人工确认/误报、规则复核 | `SEC_OPS` |
| 查询验证结果与轨迹 | `SEC_OPS`、`RULE_ADMIN` |

`ADMIN` 不自动获得此处的运维权限。角色正确但没有相应资产授权或资产已停用时返回 `40310`；客户端不能通过自报角色请求头获得操作能力。

`create_verification_router(service, *, principal_dependency=None, clock=None)` 位于 `src/api/finding_verification.py`。工厂默认没有认证依赖，所有请求按未登录拒绝。部署集成必须传入 T09 验证过的主体依赖，本次不把未接认证的路由直接挂入 `src/main.py`。`clock` 供集成与测试注入服务端时间。

## 4. 规则复核检查的是原始来源

只读规则复核采用 `RuleReview(outcome, source_sha256, reviewed_sha256, rule_version)`，由可信离线复核器提供结果，并调用 `VerificationService.review(finding_id, review, principal, *, observed_at=None)`。复核结果为 `MATCH`、`FALSE_MATCH` 或 `INCONCLUSIVE`，服务本身不包含规则引擎。

服务要求两份摘要一致，且均等于现有 Finding 的 `raw_data.source_sha256`。这说明复核对象仍是原始来源，而不是后来被修改的页面。规则复核不抓取新内容、不扫描网络、不执行破坏性请求。

| 复核结果 | 处理 |
| --- | --- |
| 原始来源匹配，结论 `MATCH` | 转为 CONFIRMED，原因 RULE_REVIEW_MATCH |
| 原始来源匹配，结论 `FALSE_MATCH` | 转为 FALSE_POSITIVE，原因 RULE_REVIEW_FALSE_MATCH |
| 缺少原始摘要、来源不一致或结论不确定 | 返回 40903，保留 OPEN，记录 BLOCKED |

规则版本、结论及来源摘要一起计算 `review_sha256`，审计中保留该摘要。后来页面已修复、删掉内容或新采集无命中，不证明第一次检测是误报；这种前后对比交给 T25 复测闭环。

## 5. 状态和审计如何一起保存

`SqlAlchemyVerificationRepository(session_factory)` 使用真实数据库事务。成功操作按条件更新 Finding，再写现有 AgentLog 的 `SUCCESS` 审计；两步在同一事务中提交。本地测试验证审计 flush 失败时，未提交的状态更新也回滚。如果连接或提交确认异常，接口返回 `50000` 并提示查询当前状态后重试，避免在提交结果未知时误报确定结论。

状态更新使用比较并交换（CAS），在 UPDATE 中同时检查仍为 OPEN 且资产仍启用、未删除。规则复核额外检查原始来源摘要未改变；若读取后被替换，返回 `40902` 并记 `BLOCKED`，不转换状态。同样的条件避免后来的验证覆盖先完成的确认结果。进入服务的权限、范围、参数和复核等拒绝动作记录 `BLOCKED`，错误只记录数字码，不留请求原文。

AgentLog 的紧凑 JSON 摘要不超过 500 字符，部分事件信息沿用操作者、任务、时间等既有列。保存前、读取后都校验字段及值，防止合法键被填入任意原文。查询时展开操作者、时间、原状态、目标状态、固定原因与方式，以及允许的摘要信息。说明正文和原始证据不随轨迹返回。

成功变更返回 `findingId`、`scopeId`、`taskId`、`status` 及 `verification` 事件，事件包含 `actor_id`、`at`、`from_status`、`to_status`、`reason_code`、`result`、`error_code`、`method` 等安全字段。

补充读接口 `GET /api/findings/{id}/verification` 返回当前状态及脱敏 `trail`。服务查询入口 `get(finding_id, principal, *, limit=100)` 默认返回最近写入的 100 条，最多 200 条，按审计 ID 倒序；本次未提供完整历史分页。它是 T22 的可查询读模型，完整 Finding 详情仍由基线 `GET /api/findings/{id}` 的后续实现负责。

## 6. 错误如何识别

| 项目错误码 | 使用场景 |
| --- | --- |
| `40001` | 无效参数、非法目标状态或原因组合 |
| `40100` | 缺少可信有效主体 |
| `40300` | 角色不能执行当前操作 |
| `40310` | 资产超出主体授权范围 |
| `40400` | Finding 不存在 |
| `40902` | 已非 OPEN 或 CAS 并发冲突 |
| `40903` | 原始来源不足、不一致或规则复核不确定 |
| `50000` | 事务、审计或查询失败，响应不含数据库原始异常 |

接口统一使用 `{code, message, data}`。自带的路由包装把损坏 JSON 和请求校验异常转为安全 `40001`，不复制框架错误中的原始输入。损坏请求体未进入业务服务，因此不声称已有业务审计；可解码但语义不合法的请求会走服务授权与拒绝审计。非法 Unicode 说明、非字符串复核 outcome 等也返回 `40001`，不回显非法值。
