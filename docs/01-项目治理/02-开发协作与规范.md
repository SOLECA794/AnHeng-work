# 02 · 开发协作与规范

> 适用范围：全部开发与测试人员；规格变更遵循 `specs/README.md` 的 SDD 治理规则。

## 1. Git 与分支

- 分支：`main`（稳定可演示）、`dev`（集成分支）、`feature/xxx`（功能分支）、`fix/xxx`（缺陷分支）；
- 流程：从 `dev` 拉取功能分支 → 开发自测 → 合并请求 → 评审合并 `dev`；阶段完成合并 `dev → main`；
- 提交信息：`类型: 内容`（feat / fix / docs / refactor / test / chore）；
- 禁止直接向 `main` 提交开发代码；合并前完成自测与冲突处理。

## 2. 代码规范

- 能力服务：Python 3.11 + FastAPI；分层路由 → 服务 → 数据；路由层不写业务逻辑；工具适配统一实现 `ToolAdapter`；
- 管理端：组件大驼峰、方法小驼峰；API 请求集中 api 目录；页面不散写请求；
- 命名：状态字段语义值大写、工具名小写点分（如 `nuclei.scan`）、时间字段 `xxxAt`；
- 安全编码：不将密钥/Token 硬编码；SQL 一律参数化；输出脱敏（证据、样例、日志参数）。

## 3. 接口规范

- 遵循 `specs/02-设计规格/SDD-03-接口规格.md`；统一响应与错误码；
- 字段变更同步 Apifox 与规格文档；写接口做参数与角色校验；
- 智能体对话接口限流；对外接口不泄露内部实现细节。

## 4. 数据库规范

- 遵循 `specs/02-设计规格/SDD-02-数据模型设计.md` 约定；
- 脚本纳入版本管理；结构变更走增量迁移脚本并先评审后执行；
- 变更后同步更新 SDD-02 对应表与变更记录。

## 5. 文档规范

- 规格文档（specs/）与治理文档（docs/）职责分离；
- 标题层级、编号、术语统一；需求变更先改规格（评审）再改实现；
- 变更记录表必填（版本、日期、变更人、内容、影响范围）。

## 6. 测试规范

- 遵循 `specs/03-测试规格/TEST-01-测试计划与用例设计.md`；
- 核心功能覆盖正常、边界、异常、越权、未授权五类场景；
- 检测效果评估基于统一测试集（版本管理），指标口径写入测试报告；
- 缺陷保留复现步骤与修复记录；核心闭环每次迭代后回归。

## 7. 安全合规要求（开发阶段强制）

- 所有检测入口执行授权边界校验（未授权返回 40310 并留痕）；
- 工具运行遵循非破坏白名单；禁止利用类参数与动作；
- 限速参数默认开启；日志审计全量记录；敏感数据脱敏。
