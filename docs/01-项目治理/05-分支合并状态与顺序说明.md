## 1. `main` 上的现存缺陷（最要紧）

C 组于 2026-10-12 将 T15–T17 适配器推上 `main`，但随后真机验证发现的两个缺陷**只修在分支上**：

| 缺陷 | `main` 上的现状 | 后果 |
| --- | --- | --- |
| 限速单位错 60 倍 | `src/tools/adapters/nuclei.py` 仍把 manifest 的「每分钟」直接传给 nuclei 的 `-rate-limit`（单位是**每秒**），实测发出 `-rate-limit 30` = **1800 次/分钟**，而 manifest 声明 30 次/分钟 | 目标承受 60 倍负载，违反验收标准 §4「目标负载受控」；实测把 DVWA 打到无响应 |
| ZAP 被动扫描漏报 | `src/tools/adapters/zap.py` 无任何等待被动队列的代码 | ZAP 被动扫描是异步的，`accessUrl` 后立刻读告警 → **被动结果 100% 漏报**（实测 0 条，队列排空后 6 条） |

另：`main` 上没有 T12/T13（授权资产与巡检计划服务），也没有适配器的容器模式。

修复均已完成、有回归测试，位于 `feature/c-tool-container-mode`（见 §3）。

## 3. 建议合并顺序

以下顺序**已实测**：每条都能干净合并，且合并完成后单测通过。

```
① spec/sdd-02-malicious-script        # 先修规格，消除 main 的枚举不一致
② feature/c-sqlalchemy-repositories   # T12/T13 + 落库（含已被取代的 c-assets-schedules）
③ feature/c-tool-container-mode       # 修复 main 上的两个缺陷 ← 优先级高
④ feature/b-registry-hardening        # 注册表加固
⑤ feature/d-t21-findings              # D 组
⑥ feature/e-admin-init                # E 组
⑦ feature/d-t20-sensitive-offline     # 需人工解冲突（§5）
⑧ feature/d-t22-finding-verification  # 需人工解冲突（§5）
```

**为什么 ③ 要早**：它修的是 `main` 上正在生效的缺陷（§1），越早合入，其他人基于 `main`
开发/演示时越不容易踩坑。① 紧随其后即可消除规格与代码的不一致。

## 5. 冲突热点与处理建议

两条冲突分支的问题**不在业务逻辑，而在「人人都改」的共享文件**：

| 文件 | 冲突原因 | 建议 |
| --- | --- | --- |
| `src/core/errors.py` | D 与 C 都新增了 SDD-03 定义的错误码（`40901`/`40902`/`40903`） | 取并集即可，注意不要重复定义同一个码 |
| `src/tools/contract.py` | D 的 T20 与 B 的加固都动过工具契约 | 以 B 的 `feature/b-registry-hardening` 为准（它已明确 §6 运行时语义），D 侧适配 |
| `requirements.txt` / `requirements-test.txt` | 各人各自追加依赖 | 取并集，按「运行依赖 / 测试依赖」分文件归位 |
| `tests/README.md`、`03-待办事项清单.md` | 多人并行追加小节 | 取并集，注意小节顺序与编号 |

**建议**：这几类共享文件是并行开发的固有冲突源，建议合并后由组长定一次「谁负责收口」，
避免每轮都重复解。

## 6. 合并前置检查

对每个分支合并前建议确认：

1. 该分支的单测在**合并后的工作区**上通过（不只是在自己分支上通过）；
2. 若涉及规格（`specs/`），确认评审已过（如 ①）；
3. 合并后跑一次 `python -m unittest discover -s tests/unit -t tests/unit` 与集成测试
   （集成测试需要 Docker：`dvwa`、`anheng-pg` 容器；不可用时相关用例会**优雅跳过**，属预期）；
4. `main` 合并完成后，请把本文件状态更新为「已合并」并登记变更记录。
