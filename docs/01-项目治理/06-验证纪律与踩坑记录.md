# 06 · 验证纪律与踩坑记录

- 状态：v1.0（2026-10-15）
- 提出方：C 组
- 用途：记录本项目在**真机验证**中反复踩到的一类问题，并给出可执行的纪律。
  适用于所有做真机验证的成员（T41/T42 执行时尤其相关）。
- 配套：仓库根目录 `CLAUDE.md` 已把本文四条铁律写入，供 AI 助手每次会话加载。

## 0. 为什么要写这个

C 组在 2026-10-13 ~ 10-15 的真机验证中，**同一类错误犯了 9 次**，每次都以
「得出错误结论 → 按错误结论行动 → 返工」收场，其中一次白重建了一个容器。

这类错误**不是"不小心"**，而是有明确的结构性根因，可以靠纪律消除。

## 1. 四条铁律

### 铁律一：无正对照，不下否定结论

> 报「没有 / 0 / 空 / 不存在」之前，先证明**这个探针能给出「有」**。

「什么都没发生」是最容易被误读的信号：它同时意味着「真的没有」和「我的观测方式坏了」，
而后者往往更常见。**正对照**（positive control）用来区分这两种可能。

### 铁律二：测的对象必须与结论的对象一致

> 结论关于 A，就要从 A 取数；不要拿 B 代替，哪怕 B 看起来"等价"。

代理物（proxy）与被测对象之间常有细微差别，正是这些差别会造成误判。

### 铁律三：测试断言需求，不断言当前值

> 写下断言前自问：**「实现错了，这条断言会失败吗？」** 不会失败的断言是废测试。

照实现写的测试会「通过」，但它证明的只是"代码现在的行为就是这样"，不是"代码是对的"。

### 铁律四：真机验证走脚本，证据落仓库

> 结论若只在对话里或终端滚动区里，等于没有证据。

## 2. 九次踩坑记录

| # | 当时的结论 | 真相 | 根因 | 代价 |
| --- | --- | --- | --- | --- |
| 1 | 「命名卷导致扫描 0 命中」 | 授权靶场容器已死（`Exited (137)`）；用命名卷与用 Windows 挂载**结果一致** | 命令加了 `2>/dev/null`，把 Docker 连接失败藏掉了 | 方向误判，多轮无效排查 |
| 2 | 「靶场没有被跳过」 | **无法判定**——nuclei 的 `-silent`（"display findings only"）本就压掉 `Skipped as unresponsive` 告警 | 拿「被抑制后的空 stderr」当作「没发生」的证据 | 结论无效，需重做 |
| 3 | 「限速测试通过」 | 测试断言 `int(value) == 30`，正是当时**错误的**值（实际应按分钟换算） | 测试照着实现写，而非照需求写 | bug 被固化，直到真机扫出问题才暴露 |
| 4 | 「超时后容器终止失败」 | 终止**成功了** | 用 `docker ps -a` 计数（含已停止容器），应用 `docker ps` | 误报缺陷 |
| 5 | 「Apache 挂了、容器坏了」 | 容器一直正常，只是启动慢 | 镜像里**没有** `netstat`/`ss`，`grep -c apache2` 也未匹配；「查不到」被读成「没在跑」 | 白重建一次容器；最后靠 `/proc/net/tcp` 才看清 |
| 6 | 「`ghcr.io` 不可达」 | 无法用 curl 判定——**拉镜像由 Docker 守护进程完成**，与 shell 的 curl 走的路径不同 | 探针与被测通道不一致 | 误判网络问题 |
| 7 | （隐含）「日志文件不存在」 | `ls` 对不存在文件的报错文本被后续 `awk` 当成字段解析 | 输出格式假设 | 小 |
| 8 | 「容器内硬超时没生效」 | 一直生效，只是在 `run()` 路径里按次注入 | 打印的是 `build_command()` 的输出，而结论针对 `run()` | 误报，险些又改错地方 |
| 9 | 「非 root 方案跑不通」 | 是 Git Bash 的 **MSYS 路径转换**把 `-e HOME=/tmp` 悄悄改成 `C:/Users/...` | 未在真实环境验证传入值 | 误判方案不可行 |

## 3. 正面做法（替代写法）

| 场景 | ❌ 别这样 | ✅ 这样做 |
| --- | --- | --- |
| 判定「扫不到」 | `docker run ... 2>/dev/null`，看到 0 条就下结论 | 保留 stderr 落盘；并用**已知会命中**的目标做正对照 |
| 判定「目标被跳过」 | 看空的 stderr 推断 | 关掉 `-silent` 让告警可见；或查队列/状态接口 |
| 判定「端口在听」 | `netstat`/`ss`/`grep ps` | `/proc/net/tcp`（恒存在）；或从另一个容器实测连通 |
| 判定「容器状态」 | `docker ps -a` | `docker ps`（只看运行中），并用 `docker inspect` 看 `RestartCount` |
| 判定「适配器行为」 | 打印 `build_command()` | 注入执行器，抓 `run()` **实际执行**的命令 |
| 判定「registry 可达」 | `curl https://<registry>` | `docker manifest inspect <image>` |
| 判定「容器内能否用某命令」 | Windows 侧推测 | 进容器实测（如 `command -v timeout`） |
| 写测试断言 | `assertEqual(实际参数, 当前值)` | `assertEqual(实际速率, 规格声明的速率)` |
| 留存验证结果 | 终端读一眼 | 走 `scripts/` 下脚本，原始输出写入仓库 |
